# make-app

Сначала человек получает работающую первую версию, потом я её проверяю и улучшаю. Шагов у задачи ограниченное число
(пул), и приложение, до которого шаги не дошли, не существует: для страницы `app_make` - первое действие, большому
приложению - раздел 3.

## 1. Страница - сразу app_make

График, таблица, счётчик, форма, доска - одна страница. Для неё первым действием, вместе с оценкой шагов,
вызываю `app_make` с первой версией:

- один `index.html`, скрипт и стили внутри, сервер - `python -m http.server 8000`; `localStorage` во фрейме
  приложения недоступен (CSP sandbox, скилл html-design), поэтому данные между перезагрузками и данные, которые мне
  нужно читать или писать, - на сервере приложения с ручками (раздел 4); файлы сервера - только в папке `/data`: правка кода и пересоздание
  контейнера её не трогают, а папка кода при обновлении меняется целиком;
- без интернета: у приложения нет сети, поэтому библиотеки, шрифты и данные - внутри файла или папки, не с CDN;
  график рисую на `<canvas>` или SVG своим кодом;
- вид, тема, анимация и что разрешено странице во фрейме - скилл html-design;
- данных нет - честные примерные, подписанные как пример, и где их заменить.

Образцы, песочница и поиск до первой версии страницы не нужны: проверяю после показа.

## 2. Проверить и поправить - после показа, пока есть шаги

- Страница открывается, каждое действие работает, ошибок в консоли нет; нашла проблему - `app_update` с
  исправлением.
- Пакеты (DuckDB, библиотека графиков) - собрать и проверить в `sandbox_run` (`packages`, `files`), затем
  `app_update(app, from_job=job)`: задача копируется в приложение вместе с пакетами.
- Шагов мало - отчитываюсь тем, что есть, и называю, что не проверено; не хватает на нужное - `request_steps` с
  причиной.

Что проверяю, когда шаги есть:

- каждое состояние экрана: пусто (что сделать первым), загрузка, ошибка (что случилось и что делать), много данных;
- формы: проверка у поля сразу, понятная подпись, черновик не теряется, опасное действие - с отменой или
  подтверждением;
- вид: одна шкала отступов и шрифтов, иерархия весом и цветом, а не размером; мало рамок; светлая и тёмная тема;
  контраст текста не ниже WCAG AA; крупные цели нажатия на телефоне; работает с клавиатуры; три ширины (телефон,
  планшет, экран);
- не по шаблону: без фиолетовых градиентов и одинаковых карточек ради карточек - вид от смысла приложения и
  человека, для которого оно.

## 3. Большое приложение - сначала готовое и образцы

Сервис, несколько экранов, вход, общие данные нескольких людей. Здесь поиск окупается, и оценка шагов это учитывает.
По порядку, первое подошедшее выигрывает:

1. **Готовое приложение**, которое можно поднять, а не писать: [awesome-selfhosted](https://github.com/awesome-selfhosted/awesome-selfhosted) -
   открытые веб-приложения и сервисы по разделам (заметки, задачи, финансы, медиа, документы, дом).
2. **Образец той же формы** - беру его устройство (данные, экраны, состояния), а не вид:
   - [TodoMVC](https://github.com/tastejs/todomvc) - одно и то же todo на десятках фреймворков: списки, фильтры,
     правка на месте, сохранение;
   - [RealWorld](https://github.com/realworld-apps/realworld) - полноценное приложение одной спецификацией на многих
     стеках: лента, авторизация, профили, комментарии;
   - [app-ideas](https://github.com/florinpop17/app-ideas) - около 90 приложений в трёх уровнях с user stories
     чек-листом, бонусными фичами и готовыми примерами («Example projects»);
   - [project-based-learning](https://github.com/practical-tutorials/project-based-learning) - разборы «сделай
     приложение X» по шагам на разных языках.
3. **Механика под капотом**, если приложение само - движок, база, сервер, редактор:
   [build-your-own-x](https://github.com/codecrafters-io/build-your-own-x).
4. **Устройство большой системы**, если приложение растёт в сервис: [system-design-primer](https://github.com/donnemartin/system-design-primer)
   (масштаб, кэш, очереди, базы - с ценой каждого решения), [awesome-scalability](https://github.com/binhnguyennus/awesome-scalability)
   (как это сделано у компаний), [awesome-low-level-design](https://github.com/ashishps1/awesome-low-level-design)
   (классы и паттерны с решениями).

Данные: сводки, графики, выборки по CSV, Parquet и JSON - DuckDB (одним SQL-запросом, в песочнице он есть; для
страницы без сервера - его сборка для браузера, duckdb-wasm, внутри приложения). Своё маленькое хранение - файл JSON
или SQLite в `/data`; общие данные нескольких людей с входом - готовый бэкенд (PocketBase), не свой сервер.

Взяла чужой код - сначала лицензия источника. Откуда взято и что переделано - в манифест приложения
(`description` или `request`), чтобы было видно, на чём оно стоит.

## 4. Ручки для меня

Приложение, в котором копятся данные (трекер, журнал, список), отдаёт мне ручки: я записываю и читаю его данные
инструментом `app_call(app, tool, args)`, без браузера. Ручек - только то, что мне нужно (записать,
сводка, записи за день), обычно 2-5; остальной API для интеграций им не становится.

- Данные, которые я читаю или пишу, лежат на сервере приложения (файл JSON или SQLite в `/data`): до браузера
  человека я не дотягиваюсь. Страница ходит в тот же API.
- Сервер на FastAPI (пакет ставится через `sandbox_run`, раздел 2): ручка - маршрут с меткой `openapi_extra={"x-sam-tool": True}` (или тегом `sam`), с `summary`
  и описанием параметров; `/openapi.json` FastAPI отдаёт сам, ручки я вижу без объявления. Параметры пути
  (`/meal/{id}`) ручкой не становятся: аргументы - в строке запроса для GET и в теле JSON для POST.
- Простой сервер без OpenAPI объявляет ручки полем `tools` в `app_make` или `app_update`:
  `[{name, description, method: GET|POST, path, params: {имя: что это}}]`.
- После показа проверяю: `app_list` называет ручки приложения, `app_call` записывает и читает.

## 5. Показать и править

- Приложение делаю `app_make`, правлю `app_update` со slug из ответа `app_make` или `app_list`; страница
  появляется в мониторе. `app_make` всегда делает новое: старое приложение правлю, только когда просят именно его.
- В итоге называю slug и адрес приложения из ответа `app_make`.
- Доработку отдаю агенту одной задачей на приложение: в описании slug и «правь через `app_update(slug, ...)`»,
  иначе агент ищет исходники по диску. Идёт задача на это приложение - дополняю её `send_to_agent`, вторую не ставлю.
- Приложение открывается в каркасе SAM: навигация, тема и панели есть по умолчанию. Панель из страницы - `<script src="/static/shell/app-client.js">` и `SAMApp.openPanel({title, path или html})`; свой каркас (`shell` в `app_make`) - только когда странице нужен весь экран. Настройки, которые человек меняет сам, - `settings`, страница читает их из `sam-settings.json`.
- Одной фразой говорю, что сделала и на чём оно стоит («на основе todo из TodoMVC, с повторением по дням»).
- Правка по ходу разговора - тот же порядок: сначала `app_update` с правкой, потом проверка.
