# Лёгкие workflow стенда

Механизм проактивности SAM: она заговаривает и действует сама, без реплики человека. Повод - расписание или событие
стенда, файл в репозитории, планировщик в шлюзе; срабатывание приходит основной модели входом с источником, при
любой основной модели. Почему файлом, а не n8n и не кронами сессии - ADR-020. Кому отдаётся вход -
[main-model](architecture/gateway/main-model.md).

`gateway/workflow_spec.py` (файл и расписание), `gateway/workflows.py` (планировщик), ворота -
`gateway/heartbeat.py` и `gateway/workflow_gates.py`, сборка - `gateway/agent.py` (`build_workflows`), старт -
`gateway/main.py`.

## Термины

- **Workflow** - сценарий стенда в файле: полное имя (уникальное на стенде), повод запуска, необязательные ворота и
  шаги по очереди.
- **Повод** (триггер) - когда запускать: расписание `on.schedule` (интервал или cron) и/или событие шины `on.event`.
- **Ворота** (`gate`) - дешёвая проверка без LLM на каждом срабатывании: пустой вывод или тот же, что в прошлый раз, -
  шаги не идут; вывод ворот - повод шагу основной модели.
- **Шаг** - запрос основной модели (`main_model`) или инструмент SAM (`tool` с `with`); агент - шаг `tool: spawn_agent`.
- **Категория** (`category`) - область SAM, к которой относится workflow: подсистема или предмет (`memory`, `radar`,
  `stand`, `skills`, `care`). Категория - множество workflow: каждый входит в одно такое множество или ни в одно.
- **Метка** (`tags`) - сквозное свойство поведения, не область: меток у workflow сколько угодно, одна метка
  встречается в разных категориях. Принятые метки:

| Метка | Что значит |
|---|---|
| `proactive` | SAM начинает сама, без реплики человека |
| `speaks` | может сказать вслух |
| `llm` | зовёт модель, тратит токены |
| `service` | служебный: человек его не замечает |

Списки категорий и меток не закрыты; имя - строчные латинские, цифры, `-` и `_`.

Workflow в репозитории сейчас:

|---|---|---|
| disk-watch | stand | proactive, speaks, llm |
| stand-health | stand | proactive, speaks, llm |
| stand-silence | stand | proactive, speaks, llm |
| late-night | care | proactive, speaks, llm |

## Файл

Папка `workflows/` в корне репозитория (`SAM_WORKFLOWS_DIR`), файл `*.yml`, как workflow GitHub Actions:

```yaml
name: memory-review          # строчные латинские, цифры, - и _; идёт в источник
category: memory             # необязательно: область SAM, ноль или одна
tags: [llm]                  # необязательно: сквозные свойства, сколько угодно
on:
  schedule:
    every: 30m               # интервал s/m/h/d, или cron: "*/15 2-5 * * *" (местное время), ровно одно
gate: received_since_memory  # необязательно: функция шлюза по имени или {command: "..."}
session: voice               # необязательно, по умолчанию voice
steps:
  - name: review
    main_model: |            # текст основной модели
      ...
  - name: note
    tool: remember           # или инструмент SAM с аргументами
    with: {fact: "..."}
```

`enabled: false` выключает файл. Битый файл или повтор имени - строка в лог шлюза, остальные работают.
Категория и метки видны в `/health` и в событии `workflow` монитора.

## Выключение

`SAM_WORKFLOWS_OFF` в `.env` выключает workflow на этой машине без правки файлов; читается при старте шлюза.
Через запятую: полное имя workflow, метка `t:<метка>` (или `tag:<метка>`), категория `c:<категория>` (или
`category:<категория>`). Workflow выключен, если подошло хоть одно.

```
SAM_WORKFLOWS_OFF=late-night                  # один workflow по имени
SAM_WORKFLOWS_OFF=t:speaks                    # ночью никто не говорит вслух
SAM_WORKFLOWS_OFF=t:llm                       # без трат на модель: остаются только служебные
SAM_WORKFLOWS_OFF=c:radar,c:care,c:stand      # три категории
SAM_WORKFLOWS_OFF=late-night,t:proactive      # смешанно
```

`SAM_WORKFLOWS=0` выключает весь планировщик. Прежний `SAM_HEARTBEAT=0` выключает `late-night` и пишет строку о
замене.

## Запуск по событию

Вместо расписания или вместе с ним - событие шины стенда (`gateway/event_bus.py`, те же события, что видит монитор):

```yaml
on:
  event:
    name: user_message        # тип события шины
    where: {session: voice}   # необязательно: поля события равны значениям (сравнение строками)
    cooldown: 1m              # пауза между запусками по событию, по умолчанию 60 с
```

`collect: true` - события, пришедшие, пока workflow идёт или ждёт `cooldown`, не теряются: копятся (не больше
`SAM_WORKFLOW_COLLECT_MAX`, 50) и уходят следующим запуском одной пачкой, поводы строками подряд. Одиночное событие
идёт сразу, частые склеиваются - так проверка ответов быстрой модели (SAM-166) отвечает на одну реплику сразу, а на
поток реплик - пачкой.

Короткая запись - `event: user_message`. Событие становится поводом шагу основной модели («Событие стенда:» и поля
одной строкой JSON); ворота, если есть, проверяются после него. Пока workflow идёт, новое событие его не запускает.
Событие `workflow` самого планировщика триггером быть не может: workflow запускал бы сам себя.

## Точка решения в коде

Если «работать сейчас или нет» решает логика, решение держит workflow, а не код, который его зовёт (ADR-020, п. 11).
Код в точке решения синхронно спрашивает ворота workflow этой точки (`gateway/workflows.py`, `Decisions.consult`):

```yaml
on:
  consult: fast_voice     # имя точки в коде
gate: fast_voice_ready    # только функция: решение мгновенное, без процесса
```

Шагов у такого workflow нет: решают ворота. Пустой вывод любых ворот точки - `noop`, в шину уходит событие `workflow`
с полем `noop`; непустой - работать. Workflow на точке нет или он выключен - решать нечего, работать. Упавшие ворота
пишут строку в лог и не решают за флоу. Точки решения работают и без Mongo: им не нужны аренда и хранилище;
`SAM_WORKFLOWS=0` гасит и их. Пропавший или битый файл точки - строка в лог на старте; точки и их workflow видны в
`/health` (`workflow_decisions`).

`fast-voice.yml` - точка `fast_voice` в голосовом ходе: отвечает ли на фразу быстрая модель. Ворота
`fast_voice_ready` (`gateway/fast_voice_gate.py`) пусты, пока сессия холодная (первые `SAM_FAST_COLD_TURNS`, 2,
голосовых хода после старта шлюза) и пока идёт откат после поправок основной (SAM-168); тогда отвечает основная.

## Очередь push: способ доставки и важность

Шаг основной модели будит модель. Чтобы десять workflow в одно время не будили её десятью вызовами, каждый такой
шаг идёт через очередь сессии (`gateway/push_queue.py`, доставка - `gateway/push_dispatch.py`) с двумя свойствами:

- `delivery` - с кем лететь: `alone` (сразу и своим вызовом, ни с кем), `batch` (по умолчанию: в общем вызове
  отдельным пунктом со своим источником), `merge` (в общем вызове, текст слит с другими `merge` - однотипные поводы);
- `importance` от 0 до 1 - насколько срочно: `1` (по умолчанию) - сразу; меньше 1 - может подождать попутчиков до
  `(1 - importance) * SAM_PUSH_MAX_HOLD_S` (по умолчанию 30 с).

| Пришло | delivery | importance | Буфер сессии пуст | В буфере сессии есть ждущие |
|---|---|---|---|---|
| 1 | alone | любая | уходит сразу, один | уходит сразу, один; ждущие ждут дальше |
| 2 | batch | 1 | уходит сразу, один | уходит сразу вместе со всеми ждущими |
| 3 | merge | 1 | уходит сразу, один | то же; все merge пачки - одним блоком |
| 4 | batch | < 1 | ждёт до своего срока | встаёт к ждущим |
| 5 | merge | < 1 | то же | то же |

Пачка уходит, когда истёк самый ранний срок ждущих в сессии (все ждущие сессии разом) или когда пришло срочное
(строки 2-3, вместе с ним). Сессии друг друга не задевают. Порядок: внутри пачки - по убыванию важности, при равной - по времени прихода, слитые
`merge` - одним блоком на месте первого из них; отправки - по мере созревания. Одно сообщение идёт текстом как есть,
пачка - абзацами `[workflow:<имя>/<шаг>] текст`; источник входа - источники через `+`. Каждая отправка - событие
`workflow_push` в мониторе (`sources`, `merged`). Одинаковые тексты идут одним пунктом `[источник +N]`. Пачка не больше `SAM_PUSH_MAX_ITEMS` пунктов (50) и `SAM_PUSH_MAX_CHARS` знаков (12 000).

Пачки по местам модели (ADR-020, п. 12): мест очереди `SAM_PUSH_PARALLEL`, по умолчанию `LLM_CONCURRENCY - 1`
(при 4 - три); пачки сессии занимают все места, кроме одного, оно остаётся одиночному `alone` (при 4 местах
модели под пачки - два, ещё одно - голосу). Ждущие делятся на пачки ровно и по кругу: пачек не меньше мест под
пачки и не меньше, чем требуют пределы пунктов и знаков, в каждой и старые, и новые поводы. Пачки одной сессии
идут одновременно, не больше мест под пачки, под одним захватом её замка раздел «Очередь фраз сессии» в [agent-loop](architecture/gateway/agent-loop.md); сверх мест -
обратно в очередь.

```yaml
  - name: review
    main_model: |
      ...
    delivery: batch          # по умолчанию
    importance: 0.2          # фоновое: подождёт до 24 с, не придёт ли соседний workflow
```

Пока места сессии под пачки заняты, её новые пачки, срочные тоже, ждут и уходят сразу, как место освободится. Ждущих в
сессии больше `SAM_PUSH_MAX_PENDING` (400) - самые неважные сворачиваются в одну строку-сводку по workflow со
счётом («Ещё 40 фоновых поводов свёрнуто (перегруз очереди): memory-review 28, disk-watch 12»).

## Судьба сообщения и условные шаги

У сообщения очереди есть судьба: `acked` - модель в шлюзе отработала пункт; `sent` - ушло модели вне шлюза
(Claude Code), она подтверждает id из поля `push_ids` входа инструментом `push_ack` MCP-сервера `sam` (`POST
/sam/push/ack {"ids": [...]}`); `dropped` - тихий режим; `error` - сбой доставки. Свёрнутые в сводку получают
судьбу сводки.

Подтверждение пунктов (ADR-020, п. 13): у пачки из нескольких пунктов пункты пронумерованы, модель в шлюзе
последней строкой ответа пишет `ОТРАБОТАНО:` и номера; вслух строка не звучит. Неподтверждённые пункты уходят
повтором, после `SAM_PUSH_ATTEMPTS` (3) попыток - `error`. Одиночное сообщение подтверждается самим ответом.

Шаг основной модели с `wait_ack: <секунды>` ждёт судьбу своего сообщения; не подтверждено за срок - `not_acked`.
Следующий шаг с `if: acked` или `if: not_acked` выполняется по этой судьбе, как `if` у шага GitHub Actions:
повторить, сказать иначе, промолчать. Повтор - решение workflow, буфер сам не повторяет: повтор того же повода
модель приняла бы за новый.

```yaml
steps:
  - name: remind
    main_model: "Напомни выпить таблетку."
    wait_ack: 120
  - name: again
    if: not_acked
    main_model: "Напомни ещё раз, мягче."
```

## Результат шага и шаг ask

Результат шага - его ответ (шаг `tool` - строка инструмента, `ask` и `main_model` - ответ модели). Следующие шаги читают его
по имени: `{{имя_шага}}` в тексте и в строках `with`, `{{reason}}` - повод запуска. `if` берёт и результат:
`if: check != OK` (или `==`), сравнение без регистра и без знаков в конце («OK.» = «OK»). Ссылка на шаг, которого раньше
нет, - ошибка при разборе файла. Шаг, который ссылается на пустой или пропущенный результат (модель недоступна, шаг
пропущен своим `if`), не идёт: событие `workflow` с `skipped`. `{{reason}}` - текст события или ворот, недоверенные
данные: инструмент с ним идёт через политику и guard, как вызов модели.

`{{count}}` - сколько событий в поводе: 1 - одиночное, больше - пачка `collect`, 0 - запуск по расписанию. Имена
`reason` и `count` заняты, шаг так назвать нельзя.

Шаг `ask` - разовый вопрос основной модели без хода: без истории, без tools, без записи в беседу и без очереди push;
ответ - результат шага. Основной модели нет - результат пустой, и шаги, которые на него ссылаются, не идут.

```yaml
steps:
  - name: check
    ask: "Верен ли ответ быстрой? {{reason}} Верен - ровно OK, иначе поправка одной фразой."
  - name: fix
    tool: say_fix
    with: {text: "{{check}}"}
    if: check != OK
```

## Шаг агента

Агент запускается шагом-инструментом `spawn_agent`, тем же путём, что вызов модели (политика, судья, событие в
монитор):

```yaml
  - name: check
    tool: spawn_agent
    with: {description: "Проверь свободное место на дисках и скажи, если меньше 20 ГБ"}
```

`steps` в `with` - прикидка шагов агента; пул шагов, каналы без траты шагов и их квота - [stand](architecture/stand/stand.md), блок
«Агенты», и ADR-022.

## Планировщик

Образец - крон Hermes Agent (MIT, `oss-ref/hermes-agent`), ссылки на строки - в шапке `gateway/workflows.py`.

- Тик раз в `SAM_WORKFLOW_TICK_S` (2 с): пустой тик - одна запись аренды, слот запускается не позже чем через 2 с
  после своего срока со сдвигом.
- Состояние всех workflow читается из Mongo одним запросом при взятии аренды и дальше живёт в памяти; ближайшие
  сроки - в куче, тик вынимает только созревшие; сдвиги созревших пишутся одной пачкой (`bulk_write`).
- Выровненный cron получает постоянный сдвиг по имени в пределах `SAM_WORKFLOW_JITTER_S` (50 с), интервал - сдвиг
  первого срока не больше периода: тысячи `*/5` и `every: 1m` не стреляют в один тик.
- Новый workflow (и после рестарта без записи в Mongo) ждёт один период: рестарт шлюза не стреляет всеми сразу.
- At-most-once: следующий запуск пишется в Mongo `_workflows` до старта шагов; не записался - запуск пропущен.
- Шлюз лежал: опоздание до половины периода (от 2 мин до 2 ч) - один догоняющий запуск, больше - пропуск до
  следующего слота.
- Один процесс на стенд: аренда тика в `_workflows` (`__lease__`), второй шлюз тикает вхолостую. Без Mongo
  планировщик не стартует, строка в лог.
- Шаги идут по очереди отдельной задачей; пока workflow выполняется, следующий его запуск не начинается.
- `/health` → `workflows`: `next_run`, `last_run`, `running` по каждому; `workflow_tick` - замер последнего тика:
  созрело, запущено, сроков в куче, мс.

## Ворота

Дешёвая проверка без LLM (у Hermes - поле `monitor`). Вывод пустой или тот же, что в прошлый раз (хэш в
`_workflows`), - модель не зовётся. Иначе вывод уходит шагу основной модели после строки «Повод (проверка шлюза
без LLM):». Команда (`gate: {command: ...}`) - stdout, ненулевой код или дольше `SAM_WORKFLOW_GATE_TIMEOUT_S`
(10 с) - сбой, событие с ошибкой. Ворот-команд одновременно не больше `SAM_WORKFLOW_GATE_CONCURRENCY` (4): каждая -
процесс. Ворота одного тика делят словарь `ctx.shared`: дорогое чтение делается один раз за тик.

| Функция | Повод |
|---|---|
| `late_night` | с `SAM_LATE_FROM_H` (2) до `SAM_LATE_TO_H` (6), человек говорил за `SAM_ACTIVE_S` (10 мин); повод с точным временем |
| `received_since_memory` | фразы людей из `voice-in.jsonl` шины (и сказанные в сторону) позже прошлого срабатывания и последней записи в `_memories`, не раньше `SAM_MEMORY_REVIEW_LOOKBACK_S` (1 ч); последние `SAM_MEMORY_REVIEW_MAX_CHARS` (4000) символов |
| `fast_voice_ready` | только для точки решения `fast_voice`: непусто, когда сессия прогрета и отката нет (блок «Точка решения в коде») |

## Шаг основной модели

Источник входа - `workflow:<имя>/<шаг>`. Модель выбирается на шаг, как на ход (`main_models.pick`):

| Основная модель | Как получает шаг |
|---|---|
| `claude-code` | строка в `lead-in.jsonl` с `source`, тикер приносит её тиком `chat` |
| `llm` | ход шлюза с источником в начале текста, как пересказ итога агента: вход в историю не пишется, сказанное звучит своей репликой в паузе и попадает в историю, только прозвучав |
| `noop` | никак |

Шаг `tool` идёт тем же путём, что вызов инструмента моделью: политика, guard, события `tool_call` и `tool_result`.
Монитор показывает каждый шаг событием `workflow` (⏱): источник, кому ушёл, начало повода и ответа; сбой - красной
строкой.

| `stand-silence.yml` | 1 мин | команда `gateway.stand_silence` | надзор не отбивался дольше `SAM_STAND_WATCH_SILENT_S` (90 с) - основная проверяет health check шлюза и модулей, упавшее перезапускает сама и говорит, что надзор молчит (SAM-195) |
| `scanning.yml` | 5 мин | команда `gateway.scanning` | вопрос, где человек или что делает, для сводки дня; включается `SAM_SCANNING=1` |
| `skills-sync.yml` | 10 мин | - | `sync_skills` сверяет `.claude/skills` с памятью SAM, модель не зовётся |
| `dialogue-notes.yml` | событие `user_message` голосовой сессии, `collect` | - | основная обновляет заметки о разговоре, быстрая отвечает по ним (SAM-131) |
| `fast-review.yml` | событие `assistant_reply` быстрой, `collect` | - | основная проверяет ответ быстрой, неверный поправляет (SAM-166) |
| `fast-action.yml` | событие `assistant_reply` с `action_unbacked` | - | быстрая обещала действие без запуска - основная запускает или говорит, что не сделала |
| `fast-handoff.yml` | событие `assistant_reply` с `handoff` | - | быстрая взяла паузу - основная отвечает по существу (SAM-169) |

Workflow на ответы быстрой (`fast-review`, `fast-action`, `fast-handoff`) идут только при основной `llm`
(`where: {main: llm}`): при ведущем ответ быстрой получает он сам (SAM-173, [main-model](architecture/gateway/main-model.md)).
