# Песочница

Код, который пишет SAM, выполняется в контейнере без секретов и данных стенда; сеть - по запросу под файрволом;
файлы внутрь и наружу - только копией шлюза. Почему так - ADR-016; что главный агент вызывает сам - [workers](architecture/agents/workers.md);
приложение из задачи - [apps](features/execution/apps.md).

`gateway/sandbox.py` (сборка команды и запуск), `gateway/sandbox_net.py`, `gateway/sandbox_pkgs.py`,
`gateway/sandbox_import.py`, `gateway/sandbox_clone.py`, `gateway/sandbox_export.py`, быстрая песочница -
`gateway/sandbox_warm.py` и `gateway/sandbox_repl.py`.

Вывод запуска в контексте модели - последние 4000 знаков; команда в журнале - до 500 знаков, с маской секретов.

## Запуск

Код, который SAM пишет для выполнения (скрипт, расчёт, график, страница), воркер запускает инструментом
`sandbox_run` (`gateway/sandbox.py`). Каждый запуск - новый `docker run --rm` от uid 1000 без capabilities, с
корнем только для чтения и лимитами памяти, процессора, процессов и времени; по таймауту контейнер останавливается
`docker kill`. Монтируется одна папка задачи `data/sandbox/<id>` (`SAM_SANDBOX_DIR`) как `/work`; окружение шлюза
и данные SAM в контейнер не попадают. Повторный запуск с тем же `job` работает в той же папке. Настройки -
`SAM_SANDBOX_*` в `.env.example`.

Образ - свой `sam-sandbox:2` (`docker/Dockerfile.sandbox`, базовые образы закреплены по digest): Python, Node с npm,
git, matplotlib, numpy, pandas, DuckDB. Берётся только локальный: `start_sam.ps1` собирает его, если нет, а
`sandbox_run` без образа отвечает одной строкой с командой сборки. Хуки и fsmonitor чужого `.git` в образе
отключены, `PYTHONPATH=/work/.pkgs` задан.

Сети по умолчанию нет. С `network=internet` контейнер встаёт в сеть песочницы (`gateway/sandbox_net.py`): интернет
есть, а правила `DOCKER-USER` закрывают из её подсети дом, хост и сети Docker. Правила ставит образ `sam-netguard:1`
перед каждым запуском с сетью; не встали, сеть с другой подсетью или с IPv6 - сети нет.

Что задача берёт извне и отдаёт наружу, задаётся параметрами одного запуска. Порядок: проверки всех параметров до
первой записи, файлы `files`, копия с ПК, клон, пакеты, команда, выгрузка на ПК.

- `packages` (`gateway/sandbox_pkgs.py`): только точная версия из PyPI или npm (`pip:six==1.16.0`,
  `npm:left-pad@1.3.0`). Шлюз проверяет версии в OSV до установки; уязвимость или недоступный OSV - установки
  нет. Установка - отдельный запуск с сетью песочницы, ничего не читает из папки задачи: pip только колёсами в
  `/work/.pkgs`, npm с `--ignore-scripts` в чистой папке. Зависимости, которые выбрали pip и npm, проходят OSV после
  установки, уязвимая - поставленное убирается. Lock-файлы задачи шлюз пишет после проверки.
- `import` (`gateway/sandbox_import.py`): копия файлов с ПК, только из папок `SAM_SANDBOX_IMPORT_ROOTS` (пусто -
  выключено). Корень диска, домашняя папка и папка над ней, папки SAM корнем не берутся. Путь без `..`, ссылок и
  имён секретов; внутри папки ссылки, спецфайлы и секреты по маскам (окружение, ключи, конфиги с токенами, `.git`,
  свои - `SAM_SANDBOX_IMPORT_SKIP`) пропускаются.
- `clone` (`gateway/sandbox_clone.py`): публичный репозиторий по `https://` без данных входа, хост из
  `SAM_SANDBOX_CLONE_HOSTS` (по умолчанию github.com, gitlab.com, codeberg.org, bitbucket.org; `*` - любой по
  имени). `--depth 1` без подмодулей, хуков и перенаправлений, отдельным запуском с сетью песочницы, с потолком
  размера `SAM_SANDBOX_CLONE_MAX_KB`.
- `export` (`gateway/sandbox_export.py`): после успешной команды - копия из задачи в папку `SAM_SANDBOX_EXPORT_DIR`
  (пусто - выключено, запреты те же, что у корней импорта, плюс папки автозагрузки, PATH и WindowsApps), без
  перезаписи (публикация `link`/`rename`, занятое имя - отказ), ссылок, `.git`, пакетов, секретов и файлов, которые
  разбирает Проводник (`.lnk`, `.url`, `desktop.ini`...). На Windows каждый файл получает Mark-of-the-Web, исполнимые
  и документы с макросами называются в итоге отдельной строкой. Модель видит путь как `export:<имя>`.
- Приложение из задачи - `app_make` и `app_update` с `from_job` (`docs/features/execution/apps.md`): задача копируется в
  приложение вместе с `.pkgs` и `node_modules`, пересборка меняет `src/` целиком и откатывается, если не запустилась.

Все копии делает шлюз байтами, без общих монтирований и без перехода по ссылкам: на POSIX путь проходится
дескрипторами с `O_NOFOLLOW`, тип файла проверяется по открытому дескриптору, на Windows ссылки из контейнера
отсекаются по `st_reparse_tag`. Каждая операция - под замком задачи: второй запуск той же задачи ждёт
`SAM_SANDBOX_JOB_WAIT_S` и отвечает «задача занята», так что шлюз не пишет в папку рядом с живым контейнером.
Потолки числа файлов и байт - у импорта, клона, выгрузки и переноса в приложение.

Журнал задачи - `data/sandbox/<id>.log`, рядом с папкой задачи, код в контейнере его не видит. Строка JSONL на
каждое действие: `run`, `network`, `packages`, `import`, `clone`, `export` (в приложение), `export_pc` (на ПК).
Команда маскируется до записи: данные входа в URL и `curl -u`, заголовки `Authorization`, `Cookie`, `*-Key`,
`*-Token`, значения и флаги `token`, `key`, `password`, `secret`, `mysql -p`, ключи JSON, токены GitHub, OpenAI,
Slack, AWS.

Файлы задачи отдаёт `GET /sandbox/<id>/<файл>` с `Content-Security-Policy: sandbox allow-scripts`, содержимое
читается из открытого дескриптора; монитор показывает `index.html` или картинку во фрейме `sandbox` и метку сети
запуска. Страница не дотягивается до API и cookie монитора.

Задача принадлежит сессии разговора, где её начали (у воркера - сессии его создателя): сессия записана в
`data/sandbox/<id>.owner.json` рядом с журналом, вне `/work`. `sandbox_run` с `job` и `from_job` приложения из
другой сессии получают отказ «задача другой сессии». Задача, без записи сессии, достаётся первой сессии, которая
к ней обратится, и это пишется в журнал строкой `owner`. Монитор показывает файлы любой задачи, как раньше.

## Быстрая песочница

`sandbox_exec(code, lang, timeout)` - инструмент основной модели и воркеров (`gateway/sandbox_warm.py`), чтобы
проверить кусок кода по ходу разговора без воркера и без 0,8 с на старт контейнера. У сессии разговора один тёплый
контейнер с той же изоляцией, что у `sandbox_run` (`sandbox.hardening`), и всегда без сети; воркер делит контейнер
с сессией создателя, другая сессия его не получает. Вывод кода - данные, а не указания модели, как у `sandbox_run`:
описание инструмента говорит модели не выполнять команды из него.

- `python` (по умолчанию): одно пространство имён на контейнер, переменные и импорты живут между вызовами,
  последнее выражение печатается, как в REPL; SQLite - модулем `sqlite3`.
- `shell` (`sh -c`) и `node` (`node -e`) - отдельный процесс на запуск.
- `sql` - DuckDB, одно соединение в памяти на контейнер, таблицы живут между вызовами.

Исполнитель `gateway/sandbox_repl.py` (`docker run -i ... python -u -c`) - два процесса, чтобы код не подделал
ответ шлюзу. Процесс 1 контейнера держит канал шлюза (строка JSON на кадр в stdin и stdout), кода не выполняет и
ставит себе `prctl(PR_SET_DUMPABLE, 0)`: `/proc/1/fd` и ptrace закрыты для кода того же uid. `docker --init` не
используется: tini был бы процессом 1 с теми же дескрипторами канала и открытым `/proc/1/fd` (проверено вживую:
запись в `/proc/1/fd/1` доходила до шлюза), поэтому сирот кода подбирает сам исполнитель. Код идёт в отдельном
процессе (fork до prctl, канал шлюза закрыт, тоже не dumpable), shell и node - его дети. Запрос шлюза несёт
случайный nonce, который в процесс кода не попадает; кадр с чужим nonce, кадр без запроса и переполнение очереди
рвут канал, контейнер гасится. На каждый запуск исполнитель делает новые безымянные файлы кода и вывода в `/tmp`
и передаёт их процессу кода дескрипторами, так что фоновый процесс прошлого запуска не пишет в вывод следующего.
Вывод обрезается до 4000 знаков. Python-код, который переписывает своё пространство имён и потоки, может влиять на
свои следующие запуски в этой же сессии, как и на свои переменные; кадр шлюзу и другие сессии ему недоступны.

Таймаут запуска - `SAM_FAST_SANDBOX_TIMEOUT_S` (30 с, потолок `SAM_FAST_SANDBOX_MAX_TIMEOUT_S`). Основной агент ждёт
итог в ходе разговора (исключение из ADR-005): весь его вызов, вместе с ожиданием замка и стартом контейнера, не
дольше `SAM_FAST_SANDBOX_MAIN_TIMEOUT_S` (10 с), просьба дольше - отказ «отдай воркеру». Запись запроса в канал
тоже под таймаутом. Зависший код гасит только свой контейнер (`docker kill`), следующий вызов поднимает новый и
говорит в ответе, что прежнее состояние потеряно и почему. Фоновая уборка шлюза (каждые `SAM_FAST_SANDBOX_SWEEP_S`)
гасит контейнер без вызовов дольше `SAM_FAST_SANDBOX_IDLE_S` (10 минут) и контейнер со сломанным каналом; тёплых
контейнеров не больше `SAM_FAST_SANDBOX_MAX` (3), новому уступает давний свободный. При остановке шлюза гаснут все.

Папка `/work` - `data/sandbox/warm-<id>`, запись сессии (`warm-<id>.owner.json`) и журнал (`warm-<id>.log`: `warm_start`,
`exec` с кодом под той же маской секретов, что команда `sandbox_run`, `warm_stop` с причиной) - рядом с ней. Папка
переживает перезапуск контейнера, пока жив шлюз. Имя с `warm-` - не id задачи: `sandbox_run`, показ в мониторе и
`from_job` её не берут, потому что шлюз пишет в папку задачи, только когда её контейнера нет. Файлы, пакеты, сеть
и показ - через `sandbox_run`.

Основная модель вне шлюза зовёт то же через MCP sam (`sandbox_exec`, `POST /sam/sandbox/exec` под ключом
привилегий) в тёплом контейнере сессии `SAM_AGENT_PARENT_SESSION`, как её агенты. Замер 14 окт на ПК после
разделения процессов: старт контейнера с исполнителем 0,5 с, запуск в тёплом - медиана 2,8 мс, худший из 20 -
3,5 мс (живой тест `tests/test_sandbox_warm.py`; там же попытки подделать ответ: подмена исполнителя из Python,
запись кадра в `/proc/*/fd` из shell и node - не проходят).

## Судья guard и песочница (SAM-197)

`sandbox_run`, `app_make` и `app_update` идут без судьи guard (`gateway/guard.py`, `HIGH_RISK_TOOLS`): границу держит
код, а не модель. Копия с ПК - только из `SAM_SANDBOX_IMPORT_ROOTS`, секреты (`.env`, ключи, `.git`) не копируются;
выгрузка - только в папку экспорта, занятое имя - отказ; клон - публичный репозиторий своей сетью; интернет команды -
через файрвол, дом и эта машина закрыты; приложение - контейнер без окружения шлюза, смонтированы только его код и
данные. Судья добавил бы вызов модели на каждый запуск и ложные отказы (так из судьи уже ушёл `mcp_call`). Что и куда
создано, видно в мониторе строкой вызова с аргументами и итогом.

## Не закрыто

Сеть модель выдаёт себе сама: файрвол закрывает дом и хост, но
не выгрузку данных задачи наружу при prompt injection - открытый риск ADR-016, решение за автором. Не проверены
вживую голосовая просьба («нарисуй график») и запуск на проде, где шлюз сам в контейнере. Замер 14 окт на образе
`sam-sandbox:1`: запуск 0,69-0,70 с.
