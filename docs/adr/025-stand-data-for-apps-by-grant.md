# ADR-025: Данные стенда приложение получает через API стенда в шлюзе, по выдаче под ключом привилегий и «да» человека

**Статус:** предложено, ждёт согласования автора (SAM-185)


## Контекст

Живое приложение SAM (SAM-182, `docs/features/execution/apps.md`) - контейнер `sam-app-<id>` во внутренней сети
`sam-app-net-<id>` (`--internal`), в него смонтирована только папка `src/`, переменных шлюза нет
(`gateway/apps.py:177`, `app_argv`). Связь с миром одна: пограничный контейнер `sam-app-edge-<id>` пересылает TCP
снаружи внутрь, с порта 127.0.0.1 хоста к приложению (`gateway/apps_edge.py`). Из приложения наружу пути нет: ни к
шлюзу, ни к Mongo, ни к Qdrant, ни к радару.

Приложениям нужны данные стенда:
- доске тренажёра - трек ученика self-tutor: в памяти SAM это факты с тегами `track`, `t:<трек>`, `p:<ученик>`
  (`.claude/skills/self-tutor/SKILL.md`, раздел о хранилищах); доска читает трек и пишет итог занятия;
- радару как приложению - присутствие (`radar/presence_api.py`);
- графику расходов - свои данные из памяти.

ADR-021 оставил механизм открытым: «механизм разрешений (список API и токены сервиса) решает автор при втором
приложении»; в дополнении «Экосистема приложений» (предложено) - один API стенда по разделам прав, токен под
манифест, выдача прав - основной моделью под ключом привилегий (`gateway/privilege_key.py`). Автор 14 окт: «PocketBase -
да» как стандартный бэкенд приложений с общими данными и входом, Sandstorm - образец модели прав и связей (журнал,
14.10 05:35). Правило характера: то, что уходит наружу или от имени человека, - после его «да»
(`docs/features/character/character.md`, раздел «Что делает сама, что после «да»»).

## Решение (предложение)

API стенда для приложений живёт в шлюзе. Приложение ходит к нему с сервера своего контейнера через пограничный
контейнер, шлюз узнаёт приложение по токену и отвечает только в границах выданных прав.

1. **Запрос прав - в манифесте.** `app.json` получает список `stand`: раздел, действие (`read` или `write`),
   фильтр (теги памяти, человек, тема) и строка «зачем». Список пишет SAM в `app_make` и `app_update`. Запрос сам
   ничего не открывает: по умолчанию прав нет (нулевой профиль ADR-021).
2. **Выдача - отдельной записью.** Права лежат в `data/apps/<id>/grants.json` рядом с манифестом, вне `src/`:
   приложение их не видит и не меняет. Запись выдачи: раздел, действие, фильтр, кто выдал, когда, по чьему «да»
   (сессия и реплика), срок, если назван. Выданное не шире запрошенного в манифесте.
3. **Кто выдаёт.** Записывает выдачу только привилегированная ручка `POST /sam/apps/{id}/grants` (в
   `privilege_key.ROUTES`): её зовёт основная модель через MCP sam. Воркеры, агенты кода и само приложение ключа
   не имеют и выдать не могут. Перед выдачей основная модель:
   - для данных о людях (память с тегом `p:<человек>`, присутствие, чат) спрашивает того, о ком данные: «доске
     нужен твой трек python-interview: читать его и записывать итог занятия. Разрешаешь?»; выдача - после «да» этого
     человека, «да» записывается в выдачу;
   - для данных без людей (события самого приложения, его темы шины, общие справочники) выдаёт сама и одной фразой
     говорит, что выдала и как отозвать.
   Автор выдаёт и отзывает то же самое кнопками на странице приложений (`/apps`, `gateway/apps_api.py`). С SAM-204
   это страница шлюза в браузере, а не отдельный процесс, и ключа привилегий у неё нет (как у монитора,
   `gateway/soul_api.py`): чем она подтверждает выдачу - решить при реализации.
4. **Токен приложения.** При первой выдаче шлюз создаёт токен (256 бит, как ключ привилегий) в
   `data/apps/<id>/stand.token`. Токен монтируется только для чтения в пограничный контейнер, в контейнер приложения
   не попадает.
5. **Путь запроса.** Пограничный контейнер получает второй пересыльщик: во внутренней сети приложения он слушает
   имя `stand` и пересылает HTTP только на адрес API стенда шлюза (`SAM_APPS_STAND_URL`), только пути `/v1/...`,
   добавляет заголовок `X-SAM-App-Token` и выбрасывает такой же заголовок из запроса приложения. Код приложения
   зовёт `http://stand/v1/memory?tags=t:python-interview` и токена не знает.
6. **API стенда.** Разделы по ADR-021: память (по тегам), присутствие, события, чат, задачи. Каждая ручка вызывает
   репозиторий шлюза (`gateway/repos/`) с фильтром из выдачи: приложение передаёт теги, шлюз пересекает их с
   выданными; сырой запрос к Mongo или Qdrant из приложения не принимается. Запись в память ставит тег
   `app:<id>` и проходит тем же путём, что `remember`. Без выдачи - 403 одной строкой: «приложению <имя> не выдан
   раздел <раздел> (<действие>)». Потолки ответа и тела - как у прокси приложений.
7. **Проверка доступа.** Ручки API стенда принимают только токен приложения, ключ стенда `SAM_API_KEY` и доступ «с
   этой машины» для них не действуют: шлюз узнаёт приложение по токену, без токена - 401. Прочие ручки шлюза токен
   приложения не открывает.
8. **Отзыв.** Кнопка в панели, голосом («забери у доски доступ к треку») или срок выдачи. Шлюз читает
   `grants.json` при каждом запросе (кеш по времени изменения файла), поэтому следующий запрос после отзыва получает
   403. «Отозвать всё» и удаление приложения удаляют выдачи и токен; пограничный контейнер перезапускается без
   токена.
9. **Что видит монитор.** События `app_grant` и `app_revoke` (приложение, раздел, действие, фильтр, кто и по чьему
   «да»); каждый отказ - событие `app_stand_denied`; обращения - сводкой раз в минуту на приложение (раздел, число
   чтений и записей), чтобы не забивать поток. Карточка приложения в панели показывает запрошенное, выданное и
   кнопку отзыва у каждой выдачи.
10. **PocketBase** остаётся бэкендом собственных общих данных приложения (ADR-021): он живёт в контейнере
    приложения или рядом с ним в его внутренней сети. Данные стенда в него не копируются.

Порядок: токен и второй пересыльщик в пограничном контейнере; `grants.json` и привилегированная ручка выдачи;
раздел памяти по тегам (доска тренажёра - первый клиент); события в мониторе и выдачи в панели; затем присутствие,
чат и задачи. Темы шины NATS (ADR-021) - тот же список выдач, раздел `bus`, когда появится шина.

## Рассмотренные варианты

**Прокси стенда в шлюзе с токеном приложения и списком разрешённых API (выбран).** Шлюз уже держит репозитории,
проверку доступа и ключ привилегий; правда о данных остаётся в Mongo и Qdrant, копий нет; отзыв действует со
следующего запроса; монитор видит каждое обращение, потому что оно идёт через шлюз. Цена: второй пересыльщик в
пограничном контейнере с разбором HTTP (сейчас там только TCP, стандартная библиотека), ручка на каждый раздел,
нагрузка обращений приложений на процесс шлюза (ADR-021 выносил приложения из шлюза ради его нагрузки), а
приложение без своего сервера (статическая страница) данных не получает - ей нужен маленький сервер.

**Снимок данных в папку приложения по запросу.** SAM выгружает выданные данные файлом в `src/stand/` (как `export`
песочницы), приложение читает файл. Отклонён как основной путь: снимок устаревает с первой новой записи трека;
записать обратно можно только файлом-ящиком, который шлюз разбирает, - вторая очередь; отзыв не забирает уже
отданную копию; запись в `src/` мешает обмену `src.new` при `app_update`. Цена отказа: нулевой сетевой путь из
приложения и работа без шлюза. Годится позже для тяжёлых выгрузок только на чтение (сводка за год в DuckDB).

**Отдельный сервис данных - PocketBase с правами на коллекцию.** Один PocketBase стенда; SAM публикует выданное в
коллекции (`tutor_tracks`, `presence`), приложение получает учётную запись PocketBase с правилом на коллекцию,
ходит к нему через пограничный контейнер. Даёт готовые вход, правила доступа, REST, подписки на изменения и
панель администратора. Отклонён для данных стенда: две правды (память в Mongo и копия в PocketBase) и синхронизация
в обе стороны - итог занятия, записанный доской в PocketBase, надо переносить в память SAM и разрешать конфликты;
отзыв - удаление копии и учётки; ещё один процесс стенда с паролем администратора. Теряем: готовые правила и
подписки - правила заменяет `grants.json`, подписки - темы NATS. Для собственных общих данных приложения PocketBase
остаётся стандартом (пункт 10).

**MCP: приложение - клиент MCP стенда.** Приложение зовёт инструменты SAM (`memory_search`, `remember`) через MCP.
Отклонён: агрегатор MCP (`mcp/mcp_aggregator.py`) не различает клиентов и открыл бы приложению всё, вплоть до
`run_command` на ПК; урезать его по клиенту - писать ту же проверку выдач, только внутри MCP; ответ инструмента -
текст для модели, приложению нужны данные с полями. Теряем: готовый протокол и список инструментов. MCP остаётся
транспортом коннекторов в обратную сторону, когда SAM зовёт приложение (ADR-021).

**Общий ключ стенда `SAM_API_KEY` приложению.** Отклонён уже в ADR-021: приложение с ключом видит всё.

## Риски и что с ними делаем

| Риск | Что происходит | Чем закрыт |
|---|---|---|
| Приложение просит лишнее | Сделанный по ошибке код читает чужие треки или всю память | Выдача не шире запроса в манифесте и фильтра; данные о людях - после «да» человека; каждая выдача видна в мониторе и панели |
| Модель выдаёт сама себе по подсказке из данных | Текст в памяти или странице уговаривает основную модель выдать права | Для данных о людях ручка выдачи сверяет ссылку на «да» с историей сессии: реплика есть, сказана этим человеком и после вопроса о выдаче; иначе отказ. Опознание говорящего по голосу - веха 0.7, до неё «да» принимается из чата монитора и голоса домашнего |
| Токен утёк | Кто-то с токеном читает выданное | Токен только в пограничном контейнере; ручки API стенда слушают адрес, доступный пограничным (проверка вживую); «отозвать всё» меняет токен |
| Агент с командой оболочки правит `grants.json` | Права появляются мимо ручки выдачи | На той же учётке ОС это не граница, как у ключа привилегий; граница - отдельный пользователь ОС для агентов (SAM-178); шлюз пишет в монитор выдачи, которых нет в его журнале выдач |
| Приложение дотягивается до Mongo или Qdrant | Чтение базы мимо прав | Контейнер приложения во внутренней сети без выхода; пересыльщик `stand` ходит только на `SAM_APPS_STAND_URL` и пути `/v1/`; ручки зовут репозитории с фильтром, сырой запрос не принимается. Открыто: Mongo и Qdrant в dev опубликованы на всех адресах хоста без пароля (`docker/docker-compose.dev.yml`, `27017:27017`, `6333:6333`) - пограничный контейнер с обычной сетью до них достаёт; пересыльщик туда не ходит, но привязку к 127.0.0.1 стоит сделать отдельной задачей |
| Адрес хоста из пограничного контейнера разный | На Docker Desktop работает `host.docker.internal`, на Ubuntu его нет без `--add-host host.docker.internal:host-gateway` | `SAM_APPS_STAND_URL` из конфига; проверка вживую на обоих |
| Шлюз лежит | Приложение без данных стенда | Приложение отвечает одной строкой «стенд недоступен» и показывает своё; шлюз и приложение перезапускаются независимо |
| Много обращений | Приложение опрашивает стенд в цикле и грузит шлюз | Потолок частоты на токен; сводка обращений в мониторе показывает виновника |

## Последствия

| Обязывает | Что даёт |
|---|---|
| Данные стенда приложению - только ручками `/v1/...` API стенда в шлюзе с проверкой выдачи | Одно место, где видно и проверяется, что приложение читает и пишет |
| Манифест перечисляет запрошенные разделы с «зачем»; выдача - отдельной записью вне `src/` | Запрос и выдача различимы, приложение себе прав не дописывает |
| Выдача - только ручкой под ключом привилегий; данные о людях - после «да» человека, «да» в записи выдачи | Человек знает, какое приложение видит его данные, и может отозвать |
| Выдача, отзыв и отказ - события монитора; выдачи - в карточке панели | человек видит, у кого что открыто |

| Запрещает или ограничивает | Чем платим |
|---|---|
| Приложению - путь к Mongo, Qdrant, MCP и прочим ручкам шлюза | Под каждый вид данных - ручка API стенда |
| Копии данных стенда в PocketBase или в папке приложения как источник правды | Нет готовых подписок PocketBase на данные стенда; подписки - через шину |
| Токен приложения в его контейнере | Второй пересыльщик с разбором HTTP в пограничном контейнере |
| Статической странице без сервера - данные стенда | Приложению с данными стенда нужен свой маленький сервер |

## Проверка

Тест-критерии SAM-185:
- приложение с выдачей `memory/read` по тегу `t:<трек>` читает факты трека; факты другого трека и другого человека не
  приходят, даже если приложение передало их теги;
- приложение с выдачей `memory/write` пишет итог занятия, факт получает тег `app:<id>`; без выдачи записи -
  403 одной строкой;
- приложение без выдачи получает 403 с именем раздела; без токена - 401; токен приложения A не открывает данные
  приложения B и прочие ручки шлюза;
- после отзыва следующий запрос - 403; после удаления приложения его токен не принимается;
- ручка выдачи без ключа привилегий - 401; выдача раздела с данными о людях без записанного «да» - отказ; выдача
  шире манифеста - отказ;
- вживую (маркер `integration`, как `test_live_app_is_isolated_and_comes_back`): из контейнера приложения
  соединение с `host.docker.internal:27017`, `:6333`, `:8000` и адресом MCP не устанавливается, `http://stand/v1/...`
  отвечает; запрос через `stand` на путь вне `/v1/` - отказ;
- монитор получает `app_grant`, `app_revoke`, `app_stand_denied`.

## Открытые вопросы автору

1. Данные о людях: «да» даёт тот, о ком данные, или достаточно «да» человека с ключом команд? Предложено - тот, о ком
   данные (трек другого человека - его «да»).
2. Данные без людей SAM выдаёт сама с одной фразой - или тоже после «да»?
3. Выдача бессрочная до отзыва или со сроком по умолчанию?
4. Нужен ли страничный путь: страница приложения в браузере читает данные через `/apps/<id>/_stand/...` без
   своего сервера? Видят их те же, кто видит страницу, но запись пойдёт мимо кода приложения.
