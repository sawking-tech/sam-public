# ADR-026: Агент правит ядро в изолированной копии, в рабочее дерево правка попадает после проверки

**Статус:** предложено, ждёт согласования автора (SAM-216)


## Контекст

Ядро SAM - репозиторий вне папок периферии (`gateway/core_paths.py`, `SAM_PERIPHERY_DIRS`, по умолчанию `data/apps`).
Привилегированный вызов (`claude_delegate` по ядру, `set_env`, `tune_self` и другие из `gateway/command_auth.py`)
выполняется только в ходе, где человек назвал секрет `SAM_COMMAND_SECRET`. Признак секрета живёт в ходе
(`secret_scope`), до воркера он не доходит, и агент правку ядра сделать не может. С 328f4e7 агент получает отказ
«Правка ядра агенту без права запрещена: подготовь разбор, план и diff и верни создателю».

15 окт агентам SAM дали две правки ядра: пул Docker и вёрстку каркаса. Оба упёрлись в судью, один спросил ключ у
создателя, другой выдумал свой. Решение автора 15 окт (журнал, SAM-216): отдавать право правки ядра агенту без контекста
опасно; без проверки того, что агент хочет править, право ниже не выдаётся; правка, сделанная по выданному праву,
лежит на выдавшем. Пути, которые автор назвал: правит основная модель в ходе с секретом; агент отдаёт план и diff, право
применить даётся после проверки; правка в изолированной копии.

## Решение (предложение)

Агент правит ядро только в изолированной копии; в рабочее дерево правку переносит тот, у кого право, после проверки.

1. Копия - git worktree репозитория на ветке задачи в `data/worktrees/<id задачи>`. Папка входит в периферию
   (`SAM_PERIPHERY_DIRS`), поэтому `claude_delegate` с рабочей папкой в копии ключа не требует, судья его пускает.
   Копию заводит инструмент `core_workspace(task)` агента: worktree, ветка `agent/<id>`, путь в ответе.
2. Агент в копии правит, гоняет тесты и коммитит в свою ветку. Итог задачи - ветка, `git diff --stat` против `dev`,
   прогон тестов и разбор: что, зачем, чем проверено.
3. Перенос в рабочее дерево - привилегированный шаг `core_apply(task)`: cherry-pick коммитов ветки в `dev` без
   переписывания истории. Его делает основная модель в ходе с секретом или ведущая сессия Claude Code, после чтения diff.
   Монитор показывает diff карточкой задачи; выдавший виден в журнале.
4. Перенос не прошёл (конфликт, тесты в рабочем дереве красные) - откат cherry-pick, задача возвращается агенту с причиной.
5. Копия удаляется после переноса или по сроку `SAM_CORE_WORKSPACE_TTL_H`; ветка остаётся до удаления задачи.

Путь «право после плана» (агенту выдаётся право править рабочее дерево по проверенному плану) этот ADR не вводит:
копия даёт ту же проверку до попадания в ядро без нового вида прав и без правки живого стенда агентом посреди работы.

## Рассмотренные варианты

- **Право command у задачи, наследуется детьми.** Отвергнуто автором 15 окт: право уходит агенту без проверки и
  размножается вниз.
- **Право после проверенного плана.** Агент пишет план (файлы, суть, проверка), создатель выдаёт право на перечисленные
  файлы на время задачи. Нужен новый вид прав с областью и сроком, судья должен сверять пути правки с планом, а
  правка всё равно идёт в живое дерево стенда, где рядом работают шлюз и другие агенты. Сложнее копии при той же проверке.
- **Правит только основная модель в ходе с секретом.** Остаётся как есть и не отменяется; для долгих правок не годится:
  ход основной модели короткий, а правка ядра - десятки шагов.
- **Копия в песочнице Docker.** Изоляция сильнее, но агенту кода нужны Python, зависимости и Docker стенда для тестов;
  worktree на той же машине даёт прогон тестов без сборки образа.

## Риски и что с ними делаем

- Агент в копии запускает код ядра (тесты, сервисы) - это код из репозитория, как и у ведущей сессии; порты стенда
  тесты не занимают (`tests/conftest.py`).
- Две задачи правят одно место - конфликт при переносе; перенос по одной задаче, второй достаётся rebase на свежий `dev`.
- Мусор копий - срок жизни и удаление после переноса; `git worktree prune` при старте шлюза.

## Последствия

| Обязывает | Что даёт |
|---|---|
| правка ядра агентом идёт через `core_workspace` и возвращает ветку | рабочее дерево не меняется до проверки |
| применение в ядро делает `core_apply`, инструмент привилегированный | правка проходит через ход человека с ключом команд |
| отказ в правке ядра называет путь, а не только запрещает | агент знает, что делать вместо |

| Запрещает или ограничивает | Чем платим |
|---|---|
| агенту писать прямо в рабочее дерево ядра | копия и перенос ветки добавляют шаг к каждой правке |
| `core_apply` без ключа команд | правку ядра нельзя сделать в фоне, только в ходе человека |

## Проверка

Агент получает задачу правки ядра, заводит копию, правит и коммитит в `agent/<id>`; ветка видна в итоге; `core_apply`
без секрета отказывает; с секретом переносит, тесты `dev` зелёные; конфликт откатывается; копия удаляется.

## Открытые вопросы автору

1. Переносит основная модель SAM в твоём ходе с секретом, ведущая сессия Claude Code или оба пути?

3. Путь «право после плана» оставить задачей на потом или закрыть этим ADR?
