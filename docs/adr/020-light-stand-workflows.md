# ADR-020: Лёгкие сценарии стенда - workflow по файлу в репозитории, n8n - для больших

**Статус:** принято; v1 сделано (SAM-96): расписание, ворота, шаг основной модели и инструмента. 12 окт дополнено решениями для тысяч workflow (очередь push, ack, условные шаги) - принято; пункты 1-13 в коде 12 окт
(SAM-126: c991def, c774a5b, 5bd1dd0, 9f91225, 779ac6e; п. 11 - f4be46e; п. 12-13 - e3bec00, 50a5574, 5975769), замер под нагрузкой - мок-тест и стресс-тест SAM-126


## Контекст

Расписаний на стенде три вида, и все зависят от того, какая модель ведёт ход. Кроны сессии Claude Code живут
только в сессии и пропадают при выходе. Своя инициатива шлюза (`gateway/heartbeat.py`) - проверка поводов раз в
60 с в коде. n8n (`:5678`) поднят в dev-compose, сценариев SAM в нём нет. Планировщика в шлюзе нет, есть только
ворота простоя `idle_gate` (SAM-94). Напомнить основной модели раз в полчаса сохранить важное в память
(SAM-94) нечем при любой модели.

Автор, 10 окт 01:18-01:21 (SAM-94, SAM-96):
- таймеры и кроны - одна абстракция стенда для любой основной модели; срабатывание идёт основной модели как вход;
- вход несёт источник: видно, что это срабатывание расписания и какого;
- «надо разделять: n8n - для больших сложных задач, а нужно что-то типа GitHub Actions - небольшие описанные
  workflow, чтобы не требовали объёмных ресурсов».

## Решение

Workflow стенда - прежде всего механизм проактивности SAM (12 окт): своя реплика или действие по поводу, без
реплики человека. Лёгкий сценарий стенда - файл workflow в репозитории: триггер (расписание cron-выражением или событие стенда) и
шаги (инструмент SAM, запрос основной модели, запуск агента). Файлы читает и запускает один процесс в шлюзе. Шаг
«основной модели» - вход с источником `workflow:<имя>/<шаг>` через основную модель (ADR-018): Claude Code тиком,
модель в шлюзе ходом. n8n остаётся для больших сценариев.

Сделано в v1 (SAM-96) и 12 окт (SAM-126): файл YAML в `workflows/`, расписание и запуск по событию шины, ворота без
LLM, шаги основной модели, инструмента, агента и разового вызова модели `ask`, очередь push, точки решения. Поздний
час (SAM-49) и память раз в полчаса (SAM-94) - workflow. Не сделано: быстрый голос на входящее сообщение, перенос
кронов сессии (SAM-96). Устройство файла, планировщика, ворот, очереди push и шагов - `docs/features/workflows.md`.

## Решение: тысячи workflow и внимание модели (12 окт)

Workflow - механизм проактивности SAM, и их станет много: модель 12 окт - 10 000 файлов дают 60-300 тыс.
срабатываний в сутки и до 5 тыс. за один тик планировщика. Узкое место - не файлы, а внимание модели: каждый
вызов платит постоянную часть (системный промпт, история, описания инструментов - 3-13 тыс. токенов у Hermes 12
окт) и занимает канал, по которому говорит человек.

1. **Модель - только через буфер.** Крон и workflow зовут основную модель только через очередь push сессии с
   параметрами доставки: с кем лететь (`delivery`: своим вызовом, пунктом общего вызова, слиянием с однотипными) и
   насколько срочно (`importance`: срочное сразу, неважное ждёт попутчиков). Прямого вызова модели из сценария нет.
2. **Канал с учётом занятости.** Пока модель отвечает, новое копится и уходит пачкой сразу после ответа (как Нейгл в
   TCP). Голос человека идёт первым и никогда не ждёт workflow.
3. **Пачка с потолком.** Предел пачки по пунктам и знакам - из конфига, лишнее - следующей пачкой; одинаковые поводы
   схлопываются в один пункт со счётчиком источников; пункты по убыванию важности.
4. **Обратное давление.** Буфер растёт быстрее, чем модель разбирает, - самые неважные сворачиваются в строку-сводку,
   а не копятся и не теряются молча.
5. **Подтверждение (ack).** У каждого сообщения очереди записана судьба: подтверждено, отправлено, отброшено, ошибка,
   потеряно при рестарте. Модель вне шлюза подтверждает инструментом стенда.
6. **Условные шаги.** Шаг может ждать подтверждения своего сообщения со сроком; следующий шаг выполняется по условию
   `if:` от исхода, как у шага GitHub Actions. Циклов и ожиданий внутри workflow нет.
7. **Поводы без перебора.** Ближайшие запуски - в куче, событие находит подписчиков по словарю; выровненный cron
   получает сдвиг, чтобы тысячи запусков не стреляли в один тик.
8. **Ворота над общим снимком.** Ворота одного тика делят снимок состояния, команды shell - через пул с пределом.
9. **Состояние в памяти.** Состояние workflow читается из Mongo при взятии аренды, дальше живёт в памяти, в Mongo -
   пачками; at-most-once: сдвиг запуска пишется до шагов.
10. **Наблюдение.** Замер каждого тика - в `/health` и монитор.
11. **Решает флоу, а не вызывающий.** Если «работать сейчас или нет» можно решить логикой самого
    workflow, проверка живёт в нём: ворота или первый шаг при условии завершают запуск без действия (`noop`). Код,
    который запускает workflow, не решает за него. Для развилок в коде workflow бывает точкой решения
    (`on.consult: <точка>`): код синхронно спрашивает его ворота; workflow на точке нет - работать. Первая точка -
    `fast_voice` голосового хода (холодный старт и откат быстрого голоса дают `noop`, отвечает основная).
12. **Пачки по местам модели, ровно и вперемешку.** Модель с несколькими местами отвечает на четыре
    пачки по 100 поводов за время одной, а одна пачка на 400 пишет вчетверо дольше и теряет пункты в длинном
    контексте. Поводы сессии делятся на пачки ровно и по кругу, пачек не меньше мест под пачки; одно место остаётся
    одиночному и срочному, одно - голосу (замер 12 окт: при трёх полосах из четырёх мест первый токен голоса p99
    1,8 с, при двух - 0,37 с). Пачки одной сессии идут вместе под одним захватом замка сессии, ход человека ждёт.
13. **Подтверждение пунктов.** Модель в шлюзе подтверждает номера отработанных пунктов пачки строкой,
    которая не звучит; неподтверждённые уходят повтором ограниченное число раз, потом - ошибка.

Числа, переменные, формат файла и подтверждения - `docs/features/workflows.md`.

## Рассмотренные варианты

**Всё в n8n.** Отклонён автором 01:20: отдельный тяжёлый сервис и редактор ради напоминания раз в полчаса.
Теряем: визуальный редактор и готовые коннекторы для мелких сценариев.

**Кроны сессии Claude Code (как сейчас).** Отклонён: пропадают с сессией и не работают при основной модели `llm`.
Теряем: ничего.

**Расписание в коде шлюза под каждый случай (как heartbeat).** Отклонён: каждый новый сценарий - правка кода.
Теряем: проверку сценария типами Python.

**Каждый workflow зовёт модель сам, с пределом частоты.** Отклонён: предел режет поводы, а не платёж - десять
workflow всё равно платят десять раз постоянную часть вызова. Теряем: простоту прямого вызова.

**Одна сводка всех поводов раз в N минут.** Отклонён: срочное ждёт до N минут. Теряем: предсказуемый ритм вызовов.

**Ack с повторной доставкой самим буфером.** Отклонён: повтор того же повода модель примет за новый и скажет дважды;
решать, повторять ли, должен сам workflow условным шагом. Теряем: автоматический повтор.

## Риски и что с ними делаем

| Риск | Что происходит | Цена | Чем закрыт |
|---|---|---|---|
| Шлюз упал | Расписание стоит | Пропуски поводов на время простоя | Вкладка и надзор поднимают шлюз; опоздание до половины периода догоняется одним запуском |
| Срабатывание принято за реплику человека | Модель отвечает вслух не по делу | Неуместная реплика | Источник `workflow:` во входе |
| Workflow разрастается в большой сценарий | Процесс шлюза грузится | Задержки хода | Граница: большое - в n8n |
| Каждый workflow будит модель сам | Десять вызовов вместо одного, канал занят, человек ждёт | Токены в 7-10 раз больше (модель 12 окт) | Модель только через буфер (п. 1), голос первым (п. 2) |
| Склейка задерживает | Неважное сообщение приходит позже | До 30 с на фоновое | Срочному `importance: 1` - уходит сразу; срок задаёт сам workflow |
| Пачка раздувается | Окно модели переполнено, качество падает на длинном входе | Пропущенные пункты | Потолок пачки, дедуп, порядок по важности (п. 3) |
| Перегруз буфера | Очередь растёт без конца | Память, задержка всего | Сводка неважного (п. 4) |
| Повод потерялся | Модель не получила или упала посреди хода; рестарт со ждущими в памяти | Молча не сказанное | Ack и условные шаги (п. 5-6); потеря при рестарте видна исходом «потеряно» |
| Workflow запускает сам себя | Событие собственного шага или очереди снова запускает его | Бесконечные вызовы модели | Свои события планировщика и очереди - не триггер; пауза `cooldown` не меньше минимума |
| Тысячи файлов на тике | Перебор и чтение Mongo по каждому, процесс на каждые ворота | Тик дольше периода | Куча запусков, снимок для ворот, пул команд, состояние в памяти (п. 7-9) |
| Пик на круглых минутах | Тысячи срабатываний в один тик | Всплеск пачек | Случайный сдвиг cron в пределах минуты (п. 7) |

## Последствия

| Обязывает | Что даёт |
|---|---|
| Сценарий стенда - файл в репозитории с триггером и шагами | Сценарий видно в git, правится без кода |
| Срабатывание идёт основной модели входом с источником | Работает при любой основной модели |
| Модель - только через очередь push с `delivery` и `importance` | Один вызов вместо многих, канал свободен для человека |
| Исход каждого сообщения очереди записан (ack) | Flow знает, услышан ли повод, и решает, что дальше |

| Запрещает или ограничивает | Чем платим |
|---|---|
| Новые расписания кронами сессии или кодом шлюза | Расписание кронами сессии живёт, пока они не перенесены в файлы (SAM-96) |
| Тащить в лёгкий workflow большие сценарии | Граница «лёгкий - большой» решается на глаз |
| Прямой вызов модели из workflow | Фоновое сообщение может подождать попутчиков |
| Циклы и ожидания внутри workflow | Повтор - новым срабатыванием или условным шагом по ack |
