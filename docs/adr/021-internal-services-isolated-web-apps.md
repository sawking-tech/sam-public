# ADR-021: Внутренние сервисы - изолированные веб-приложения на платформе SAM

**Статус:** принято; сделан радар (SAM-105), монитор и сервис документов впереди; экосистема приложений (14 окт) - предложено


## Контекст

Радар присутствия жил внутри шлюза: маршруты в `gateway/main.py`, цикл опроса роутера в его процессе. Автор
10 окт 2026 заметил «жёсткую неоптимальность работы» и лаги системы, и сказал выносить монитор и сканер в
самодостаточные веб-сервисы. Следом назвал третье приложение: сервис учёта налогов и квитанций, вообще
документооборота («для дома или ещё чего-то»).

Слова автора:
- «радар можно считать отдельным изолированным веб-приложением, которое реализовано на платформе SAM»;
- «потом таким же станет и монитор»;
- «не важно какой сложности эти приложения»;
- «они могут брать данные от SAM-стенда, которые он позволит им через интерфейсы, или выдавать наружу для
  сохранения, которые он позволит тоже; всё остальное внутри, пользователь видит UI в окне»;
- «SAM будет писать в песочнице и потом, что готово, сохранять, и тем самым обрастать со временем
  дополнительными фичами, или просто артефактами, мини-страничками временными, с презой или графиком, не важно».

## Решение

Внутренний сервис SAM - отдельный веб-процесс со своим портом, своим UI и своим состоянием (файлы в `data/`).
Он собран на платформе SAM: общий слой доступа (`gateway/access.py`), чтение настроек (`gateway/env.py`), запуск
скриптом стенда. Сложность не ограничена: страница-график и сервис документов - один и тот же вид.

Граница сервиса - интерфейсы стенда:
- вход: сервис получает от стенда только то, что стенд ему разрешил (HTTP-запрос, сообщение, чтение через
  разрешённый API). Прямого доступа к Mongo, Qdrant, истории SAM и процессам шлюза у сервиса нет;
- выход: наружу, в память SAM или в хранилище, сервис отдаёт только то, что стенд разрешил принять;
- остальное внутри сервиса; пользователь видит окно с UI.

Шлюз не хостит сервис и не падает вместе с ним. Сбой связи со стороны шлюза не мешает ходу чата: клиент шлёт в
фоне и молчит после ошибки (`gateway/radar_client.py`).

Жизненный цикл: SAM пишет сервис или страницу в песочнице (ADR-016), готовое сохраняет в репозиторий,
и платформа обрастает функциями. Временная страница (презентация, график) не обязана становиться сервисом и может
остаться артефактом.

Сделано в первом применении (радар): `radar/presence_api.py` (приложение над хабом), `radar/presence_service.py`
(`python -m radar.presence_service`, порт `SAM_RADAR_PORT`, по умолчанию 8010), `start_radar.ps1`, клиент
шлюза с адресом `SAM_RADAR_URL`.

## Рассмотренные варианты

**Всё в шлюзе, как было.** Отклонён автором: радар и монитор грузят процесс шлюза, каждое приложение
привязывается к его перезапускам. Теряем: один процесс и один порт.

**Микросервисы с общей базой данных.** Отклонён: сервис тянет за собой Mongo-схему шлюза, граница размывается.
Теряем: быстрый доступ к любым данным SAM без интерфейса.

## Риски и что с ними делаем

| Риск | Что происходит | Чем закрыт |
|---|---|---|
| Сервис выключен | Шлюз шлёт сообщения впустую | Клиент шлёт в фоне, после сбоя молчит 30 с |
| Сервисов становится много | Растёт нагрузка и число портов | Каждый сервис включается по флагу и запускается отдельным скриптом |
| Интерфейс «что стенд разрешает» не описан | Каждый сервис тянет данные по-своему | Открыто: механизм разрешений (список API и токены сервиса) решает автор при втором приложении |

## Последствия

| Обязывает | Что даёт |
|---|---|
| Новое приложение - отдельный процесс, порт и скрипт запуска | Шлюз и приложения перезапускаются независимо |
| Данные приложения - только через интерфейсы стенда | Граница видна в коде и в сети |

| Запрещает или ограничивает | Чем платим |
|---|---|
| Хостить приложение в процессе шлюза | Лишний процесс и порт на каждое приложение |
| Читать базы шлюза напрямую | Нужен интерфейс под каждый вид данных |

## Экосистема приложений (дополнение 14 окт 2026, предложено)

**Контекст.** Автор 14 окт: монитор и его UI - клиент приложения для работы с SAM, он получает и отдаёт данные; у
приложений есть коннекторы и вебхуки, которые SAM использует и встраивает в себя; другое приложение может быть
изолировано сильнее; степень интеграции решает SAM; всё плагинное по возможности и в одной экосистеме; границы
приложений всегда чёткие, соединить их можно только умышленно; шина сообщений с доставкой и переживанием перезапуска
- сразу, проверенная и удобная; SAM доступна в домашней сети, значит и её приложения - UI и API, если они для
интеграции; у каждого приложения свой репозиторий и бэкап; потом SAM учится делать микросервисы. Сейчас связка у
каждого своя: радар - сервис плюс инструменты MCP, прописанные руками (`mcp/radar_server.py`), монитор - страница
шлюза на его WebSocket, приложения SAM-182 - без данных стенда вовсе.

**Решение.**
- Одна экосистема: монитор, радар, сервис документов и приложения, которые сделала SAM, - участники одного вида.
  Каждого описывает манифест: что это, как запускается, профиль изоляции, права на API стенда, коннекторы.
- Профиль изоляции - в манифесте, по умолчанию нулевой (как песочница): сеть - нет, интернет или названные адреса
  дома; файлы - только своя папка; API стенда - ничего. Монитор - доверенный клиент, график - пустой профиль.
- API стенда для приложений - один, по разделам прав: события (поток), чат (прочитать, написать), память (по тегам),
  задачи. Приложение ходит с токеном, выданным под свой манифест; без токена раздела нет.
- Границы приложений всегда чёткие, соединение - только умышленное. Коннекторы - плагины: приложение описывает в
  манифесте свои ручки и вебхуки (имя, параметры, что возвращает), но объявленный коннектор ничего не подключает.
  Инструментом SAM он становится, только когда его подключили явным действием; так же приложение A видит
  приложение B, только когда их связали. Связь снимается так же явно; снимается приложение - снимаются его связи.
- Шина сообщений - NATS с JetStream. Хранится только то, что отправитель пометил важным: человек - голосовой меткой
  «важно» или флагом в мониторе, сценарий - в своём файле у шага или повода, приложение - в сообщении (задачи, итоги агентов, команды): потоки JetStream с подтверждением, переживают перезапуск. Непомеченное идёт обычными темами и пропадает,
  токены модели на него не тратятся. Важное SAM забирает сама по своей нагрузке. Те же правила между
  приложениями: важное ждёт получателя, остальное без него пропадает, получатель забирает в своём темпе. Мёртвая очередь: важное, которое
  получатель не подтвердил за `max_deliver` попыток, уходит в поток `DLQ` по событию JetStream о превышении попыток;
  оттуда его видно в мониторе, его можно повторить или удалить, а SAM получает о нём одно сообщение. Проверенный сервер CNCF, один процесс, официальный клиент `nats-py`; в dev и на
  проде - контейнер рядом с Mongo и Qdrant. Приложение публикует и читает только темы, на которые его умышленно
  подписали; право на тему - раздел API стенда, как остальные. События шлюза (`event_bus`) идут в шину темами.
- Доступ из домашней сети: SAM доступна дома, значит и её приложения. Вход один - шлюз с его проверкой доступа
  (`gateway/access.py`, `SAM_API_KEY`): UI - `/apps/<id>/`, API - `/apps/<id>/api/...`. Наружу выходит только то,
  что приложение объявило в манифесте (UI, API, оба или ничего, по умолчанию ничего), и только после умышленного
  выставления. Людям с браузера - ключ стенда и cookie, машинам для API - свой токен на приложение, отзываемый
  отдельно. Порты приложений остаются на 127.0.0.1; панель тоже открывается через вход шлюза, а не своим портом.
- У каждого приложения свой git-репозиторий в его папке: создание - первый коммит, каждая правка - коммит с
  просьбой, ради которой она сделана; откат правки - откат коммита и перезапуск. С историей SAM не смешивается.
- Бэкап: у каждого репозитория удалённый `backup` - голый репозиторий в одном жёстком месте (`SAM_APPS_BACKUP`, по
  умолчанию `Documents/sam-backups/apps/<id>.git`), пуш после каждого коммита. Вынос в удалённый репозиторий
  (проект на GitHub - позже) - только явно и по приложению: код уходит из дома.
- Приложения на компьютер не ставятся: каждое - контейнер и своя папка; удалено - на машине ничего не осталось.
- Данные приложения: файл или `localStorage` для своего, DuckDB для сводок, PocketBase (база, вход, REST, обновления
  одним файлом, MIT) - стандартный бэкенд, когда данные общие для нескольких людей; свой сервер с базой не пишется.
- Магазин MCP: MCP-сервер - участник экосистемы без UI. Готовые серверы - из каталога `docker/mcp-registry` через
  `docker/mcp-gateway` (оба MIT), под агрегатором своей машины (`mcp/mcp_aggregator.py`): SAM видит одну строку на
  машину - жива ли и что на ней, инструменты сервера открывает по запросу. Свой - только список рекомендованных и
  инструмент «поставь или сними».
- Та же шина - внутри самой SAM: самодельные шины (`event_bus` шлюза, голосовая шина файлами `data/voice/bus`,
  очередь push в основную модель) переезжают на NATS по одному потоку, начиная с событий шлюза; голосовая шина -
  последней и с замером задержки до и после, она чувствительна ко времени.
- Степень интеграции решает SAM: права и коннекторы выдаёт основная модель привилегированным действием под ключом
  привилегий (`gateway/privilege_key.py`, SAM-177); приложение выдать права само себе не может.
- Порядок: репозиторий и бэкап приложений; шина NATS; API стенда и права с выставлением в домашнюю сеть;
  коннекторы и связи из манифеста; монитор первым клиентом, радар - с коннекторами «где кто» вместо прописанных
  руками; затем перенос внутренних шин SAM на NATS.

**Рассмотренные варианты.**
- **Каждое приложение - свой MCP-сервер.** Отклонён как единственный путь: MCP закрывает «SAM вызывает приложение»,
  но не «приложение получает события и пишет в чат», и каждый сервер прописывается в агрегатор руками. Теряем:
  готовый протокол для коннекторов - его можно оставить транспортом коннектора.
- **Общий ключ стенда всем приложениям.** Отклонён: приложение с ключом видит всё, изоляция по уровням пропадает.
  Теряем: простоту одного ключа.
- **RabbitMQ.** Отклонён: тяжёл для домашнего стенда (Erlang-машина, сотни мегабайт в простое - оценка, не
  замер) и сложнее в обслуживании. Теряем: богатую маршрутизацию обменников - темам NATS она не нужна.
- **Шина в памяти шлюза (`event_bus`) без своего сервера.** Отклонён автором: нужны доставка и переживание
  перезапуска сразу. Теряем: ноль новых процессов.
- **Платформа целиком - Coolify, Dokploy, CasaOS, Umbrel.** Отклонён: рантайм, прокси и панель уже свои и
  проверены; Coolify - Laravel, Postgres, Redis и Traefik на слабом домашнем сервере и не ставится на Windows; изоляции дома и
  внутренней сети в них нет - её всё равно писать. Теряем: готовые сервисы в один клик - их заменяет поиск готового
  в `make-app` и магазин MCP.
- **Gitea для репозиториев приложений.** Отложен автором: голого репозитория с бэкапом хватает; вынос на GitHub -
  `git push` в новый репозиторий.
- **Права пишет автор руками в конфиг.** Отклонён по слову автора: степень интеграции решает SAM. Теряем:
  ручной контроль каждой выдачи - его заменяет журнал выдач и ключ привилегий.

**Риски.**

| Риск | Что происходит | Чем закрыт |
|---|---|---|
| Приложение просит лишнее | Сделанный по ошибке или подсунутый код получает данные стенда | Профиль по умолчанию нулевой; выдача - только привилегированным действием SAM, видна в мониторе и журнале |
| Коннектор подменяет инструмент SAM | Модель зовёт чужую ручку вместо своей | Инструменты приложений с префиксом имени приложения, без перекрытия встроенных |
| Модель была недоступна, накопились сообщения | После возврата модель засыпана потоком | Занятая модель - не недоступная: сообщения ждут в очереди сессии (SAM-01) и разбираются, как освободится. Недоступная - накопленное для неё выбрасывается; важное (задачи, итоги агентов, команды) лежит в потоках JetStream |
| Шина лежит | Приложения не получают сообщений | JetStream хранит неподтверждённое; шлюз и чат SAM от шины не зависят, приложение пишет одной строкой, что шины нет |
| Приложение открыто в домашней сети без нужды | Гость или чужое устройство видит его UI или API | Наружу только объявленное и выставленное явно; вход через шлюз с ключом; API машинам - по токену приложения |
| Бэкап на том же диске | Смерть диска уносит и приложения, и бэкап | Спасает от ошибки SAM и порчи папки; другая машина или удалённый репозиторий - следующим шагом |
| Связь появляется сама | Приложение видит соседа, которого ему не давали | Соединение - только явным действием SAM под ключом привилегий; по умолчанию связей нет |
| Монитор как приложение падает | Нет консоли у человека | Шлюз продолжает работать; монитор поднимается, как другие приложения; запасной терминал - TUI |

**Последствия.** Обязывает: новые части стенда с UI - приложения экосистемы с манифестом; данные стенда приложению
- только через API стенда по выданным правам; сообщения между приложениями - только через шину по темам; из домашней
сети - только через вход шлюза; правка приложения - коммит в его репозиторий и пуш в бэкап.
Запрещает: приложению читать Mongo, Qdrant и файлы стенда напрямую; выдавать права и связи без ключа привилегий;
соединять приложения неявно - через общую папку, сеть или переменную.
